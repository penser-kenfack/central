1. Background and Problem Statement

Since the start of our third year, some of us have lost belongings, or seen others lose them, in classrooms and other campus spaces. A loss is often noticed only later, so nobody knows what happened or whether someone found the item.

Students and staff may lose personal belongings such as phones, bags, keys, student ID cards, documents, books and USB drives. Found items may remain unreported, or be difficult to connect with their owners, because there is no centralized and organized system. The same problem likely exists in other universities and schools.

2. Project Objectives

2.1 General objective

Provide a centralized platform where users can report lost or found items, search reports, identify possible matches, verify ownership and record the return of recovered items.

2.2 Specific objectives

Users must be able to:

  1. Report an item as lost;
  2. Report an item as found;
  3. Search reported items;
  4. Receive possible matches between lost and found reports;
  5. Provide the information needed to verify ownership;
  6. Follow the status of their report;
  7. Have the final return recorded.

2.3 Out of scope

  • The system does not promise to recover stolen items and does not replace a report to the authorities.
  • No payments, no delivery of items, no real-time geolocation.
  • No native mobile application in version 1 (responsive web application only).

3. Scope and Main Workflow

The scope is deliberately limited to a single business workflow:

Report→Search / Match→Verify→Return→Record

We address the information-management problem: how a university can organize lost and found information and facilitate recovery.

6. Business Rules

IDRule
BR-01Only an authenticated user can report, claim or receive notifications.
BR-02A report has exactly one author and belongs to exactly one category.
BR-03The date an item was lost/found cannot be in the future.
BR-04Verification information (private fields) is never displayed publicly.
BR-05A found item can only be returned after a claim has been accepted by the officer.
BR-06A found item can have only one return.
BR-07A user cannot claim an item they reported as found themselves.
BR-08After 3 rejected claims within 30 days, the account is flagged for review.
BR-09A report with no activity for 90 days becomes Expired (lost) or Unclaimed (found).
BR-10Every return requires presentation of an identity document or student ID card.

Status life cycle

Lost item: Open → Match found → Under verification → Returned → Archived (or Cancelled / Expired)

Found item: Reported → In stock (received at desk) → Claimed → Under verification → Returned → Archived (or Unclaimed)

Main success scenario — UC-06 / UC-07 / UC-08

  1. The student receives a notification: "Possible match at 87%".
  2. They open the report, click "This is my item" and answer the verification questions.
  3. The officer compares the answers with the private details and accepts the claim.
  4. The student receives a pick-up appointment at the desk.
  5. At the desk, the officer checks the student ID, hands over the item and records the return.
  6. Both reports move to Returned; the history is kept.

10. Proposed Technical Architecture

  • Frontend: responsive web application (HTML/CSS/JavaScript, or React/Vue).
  • Backend: REST API (Node.js/Express, Laravel or Django, at the team's choice).
  • Database: relational (MySQL or PostgreSQL).
  • Photo storage: server folder or object storage, with resized images.
  • Notifications: SMTP e-mail service; in-app notifications stored in the database.
  • Deployment: university server or cloud hosting, with a test environment.

14. Acceptance Criteria

  • A student can report a lost item in under 2 minutes from a phone.
  • A matching found report triggers a match notification to the owner.
  • No private field is visible to anyone other than the lost and found officer.
  • A return is only possible after an accepted claim and the recording of an identity document.
  • The officer can see the number of lost items per location and per month.

15. Expected Benefits

  • Centralizes lost and found information.
  • Makes it easier to search for missing belongings.
  • Helps connect lost items with reported found items.
  • Provides an organized ownership verification process.
  • Keeps a history of reports and returned items.
  • A structured process helps items reach their legitimate owners.
  • The university can see which locations or periods have the most lost or found items.

16. Feasibility

The scope is defined around one workflow: Report → Search/Match → Verify → Return → Record. We do not promise to recover stolen items; we address the information-management problem of how a university can organize lost and found information and facilitate recovery.

This scope provides enough material for requirements analysis, a feasibility study, business rules, use cases, database design, system architecture, interface design, testing and deployment planning, using web technologies the team already masters.
